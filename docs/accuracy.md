# 計測精度の設計と限界

> **対象は CrackScan（iOS アプリ・近接の絶対幅計測）です。**
> σ実測ツール（web/・遠方の追跡測定）の精度は
> [web/README.md](../web/README.md) と[取扱説明書](https://kiyoshi-terrain.github.io/crack_tracking/manual/)を参照してください。

このドキュメントは「このアプリの数字をどこまで信用してよいか」を明示するためのものです。
点検調書に載る値を扱う以上、精度の根拠と限界を曖昧にしたままにはできません。

---

## 1. 精度を決めているのは何か

ひび割れ幅の計測値は、次の3つの掛け算で決まります。

```
幅[mm] = 幅[px] × スケール[mm/px] × 補正係数
          ↑         ↑                 ↑
      断面解析     LiDAR             PSF補正
```

このうち **スケール[mm/px]（GSD, 地上分解能）が支配的** です。
`幅[px]` をサブピクセルで頑張って求めても、GSD が粗ければ意味がありません。

### GSD の求め方

```
GSD[mm/px] = 撮影距離[m] × 1000 / 焦点距離[px]
```

焦点距離[px] は `ARFrame.camera.intrinsics` から取れます。画素数に比例するので、
**同じレンズでも高解像度モードのほうが GSD は細かくなります。**

---

## 2. 「0.2mm を測る」に必要な距離

幅計測には、ひび割れが最低 **3px** 程度に写っている必要があります
（`CaptureAdvisor.defaultMinimumPixelsAcrossCrack`）。
3px を下回ると、後述する PSF（レンズのボケ）の影響が幅そのものを上回り、
半値幅が真幅ではなくボケの幅を測り始めます。

必要 GSD:

```
GSD ≤ 目標幅 / 3
0.2mm → 0.067 mm/px
0.1mm → 0.033 mm/px
```

これを距離に直すと（`CaptureAdvisor.maximumDistance`）:

| 撮影モード | 焦点距離の目安 | 0.2mm を測れる距離 | 0.5mm を測れる距離 |
|---|---|---|---|
| 12MP (4032×3024) | 約 3000 px | **0.20 m** | 0.50 m |
| 48MP (8064×6048) | 約 6000 px | **0.40 m** | 1.00 m |
| 望遠 (77mm 相当, 12MP) | 約 8000 px | **0.53 m** | 1.33 m |

**これが本アプリの最大の制約です。**
「離れた場所から橋脚全体をスキャンして 0.2mm のひび割れを測る」ことは
物理的に不可能で、それはアプリの実装の問題ではなくレンズと画素の問題です。

運用としては 2 段構えになります。

1. **広域スキャン**（1〜3m）: ひび割れの位置と延長を面的に記録する。
   幅は 0.5mm 以上のものだけが有効。
2. **近接計測**（0.2〜0.5m）: 要注意箇所に寄って幅を確定させる。

撮影画面では GSD を常時表示し、目標幅を満たさない位置では
「分解能不足。◯m 以内まで近づいてください」と具体的な距離を出します。

## 3. 断面解析（幅[px] の求め方）

芯線に直交する輝度断面 p(t) を 0.25px 刻みで取り、
背景輝度 b と最小値 m の中間を横切る位置を線形補間で求めます（半値幅・FWHM）。

```
        b ─────╮                    ╭───── b
                ╲                  ╱
    threshold ───╳────────────────╳───     ← ここの間隔が幅
                  ╲              ╱
        m          ╰────────────╯
                   ├─ w[px] ─┤
```

### なぜ「線形光」で測るのか

`ImageConversion` は sRGB の逆ガンマを掛けて線形光に戻してから解析します。
理由は幾何的です。ある画素の面積の半分がひび割れに覆われているとき、
**線形光であれば** 画素値はちょうど背景と亀裂の中間になります。
つまり半値の交差点がそのまま幾何的なエッジ位置に一致する。
ガンマ符号化されたまま測ると、この対応が崩れて幅が系統的にずれます。

### 検出は縮小画像・計測は原寸

近接（0.3m・48MP）では 1mm の亀裂が 20px、3mm なら 60px に写ります。
リッジ検出は σ ≒ 線幅/2 で最も強く応答するので、幅広の開口を等倍で追うと
σ=30 級のガウシアン微分が要って数十秒かかります。一方、芯線の**位置**なら
縮小画像で足ります（数 px ずれても断面の対称性で中心を取り直す）。

そこで `AnalysisPlanner` が目標幅の px 数から縮小率を決め（目標幅が検出画像で
約 4px になるように）、`CrackDetector` は縮小画像で検出し、芯線を原寸へ戻して
**原寸の輝度断面**で幅を測ります。幅の精度は縮小率に依存しません
（`testWideCrackIsDetectedOnceAndMeasuredAtFullResolution`）。

目標幅は「測りたい幅の級」です。検出はその 0.8〜4 倍を狙うので、
石積みの数 mm の開口を 0.2mm の設定で撮ると「検出できません」になります。

### 局所背景推定

コンクリート面は照明ムラ・打ち継ぎ・型枠跡で輝度が大きく変動します。
断面の両端 25% の中央値から背景を推定することで、
画面全体の明るさムラの影響を受けません（`testWidthIsRobustToIlluminationGradient`）。

## 4. ボケと「一定の太り」— 幅の系統誤差

### 対称なボケは半値幅をほとんど広げない

矩形の断面をガウシアン σ でぼかしたときの半値幅を数値で解くと、こうなります
（`√(w²+(2.355σ)²)` は昔ここに書いていた見積り）。

| 真幅 | 半値幅（σ=0.8px） | 見積り √(w²+f²) | 半値幅（σ=1.35px） |
|---|---|---|---|
| 1.0 px | 2.01 px | 2.13 px | 3.25 px |
| 2.0 px | 2.42 px | 2.75 px | 3.48 px |
| 3.0 px | 3.12 px | 3.54 px | 3.88 px |
| 5.0 px | 5.00 px | 5.34 px | 5.22 px |
| 10.0 px | 10.00 px | 10.18 px | 10.00 px |
| 30.0 px | 30.00 px | 30.06 px | 30.00 px |

**幅が σ の 3 倍もあれば、半値幅は真幅そのもの。** 対称なボケは 50% を横切る
位置を動かさないからで、これは「線形光で測る」約束の裏返しです。近接（0.1mm/px）で
測る 1mm 級の開口は 10px 級なので、ボケは幅にほとんど効きません。

### だから「一定の超過」はボケでは説明できない

実測で見えた「どの幅にも +0.1〜0.2mm 乗る」超過は、上の表のとおりボケの形をして
いません（ボケなら細い線にだけ効く）。一定量が乗るのは

- 印刷・塗りのにじみ（線そのものが設計より太い）
- トーンカーブの非線形（線形光に戻し切れていないと、50% の高さが幾何のエッジからずれる）

のような要因です。そこで幅の補正は 2 つの項を持ちます。

```
raw = √( w² + (2.3548·σ)² ) + b
```

σ は細い線にだけ効き、b はどの幅にも同じだけ乗る。**形が違うので、既知幅を
2 通り測れば分けて決められます。**

### 現地で解く（幅校正・`WidthCalibration`）

係数は文献や事前の実験から借りません。端末・レンズ・ピント・被写体で変わるからです。
クラックスケールのような**既知幅の線をその場で測って解きます**。

1. 静止画レビューで既知幅の線をなぞって測る（先に「縦尺」を合わせておく。
   既知幅を px に直すのに分解能を使うため）
2. その線を選んで「幅校正」→ 実際の幅（mm）を入れる
3. 2 本目（太さの違う線）を入れると σ と b が分かれる。1 本だけのときは
   **σ を動かさず b だけ**を決める（1 点では 2 つの未知数は分けられない）

校正は案件に残り、次の撮影から効きます。既に測った候補も、測点に**補正前の半値幅**を
残してあるので撮り直さずに測り直せます（`CrackMeasurement.recalibrated`）。
使った σ と b は記録（CSV の「幅校正PSFσ(px)」「幅校正オフセット(px)」列）に残ります。

**3px 未満で写ったひび割れは `isResolutionSufficient = false` とし、
UI・CSV・PDF のすべてで「参考値」として明示します。**
この値を根拠に判定を下してはいけません。

## 5. 斜め撮影（スケールの異方性）

壁面を斜めから撮ると、傾いている方向のスケールだけが 1/cosθ で伸びます。

| 入射角 θ | 傾き方向の誤差（無補正の場合） |
|---|---|
| 10° | +1.5% |
| 20° | +6.4% |
| 30° | +15.5% |
| 45° | +41.4% |
| 60° | +100% |

本アプリはこれを近似で扱わず、LiDAR で求めた壁面と視線の交点を
実際に計算して距離を測っています（`SurfaceScale.millimetersPerPixel`）。
そのため幾何的には入射角によらず正しい値が出ます。

ただし**幾何が正しくても画質は落ちます**。斜めになるほど

- 被写界深度から外れる部分が出てボケる
- ひび割れの内壁が見えず開口部が細く写る

ため、25° を超えると警告、45° を超えると撮影をブロックします。

## 6. LiDAR 自体の精度

iPhone の LiDAR は測距誤差が 1〜2cm 程度あります。
これが GSD にどう効くかというと、**距離に対する相対誤差がそのまま乗ります**。

```
0.3m で撮影、LiDAR 誤差 1cm → スケール誤差 3.3%
1.0m で撮影、LiDAR 誤差 1cm → スケール誤差 1.0%
```

近接撮影ほど相対誤差が大きくなるのは直感に反しますが、事実です。
`PlaneFitter.fitRobust` が ROI 内の数百点から平面をフィットするため、
単点の測距ノイズは √N で平均化され、実効的にはこれより小さくなります。
平面フィットの残差 RMS は `CaptureConditions.planeResidual` として監視し、
2cm を超える（＝そもそも平面でない）場合は警告します。

**実測（2026-09-05、iPhone 16 Pro Max・0.27〜0.34 m・ゲージシート 6 枚）**:
静止画ごとの縦尺の倍率は 1.03・1.03・1.04・1.04・1.04・1.095 でした。系統的に 3〜4% 大きく、
ときに 10% 近く揺れます。これは幅の測り方の問題ではなく LiDAR の距離です。

そのため**スケールバー校正**を入れています（`ScaleCorrection`、静止画レビューの「縦尺」）。
亀裂の横に既知の長さ（100 mm の目印を付けたテープなど）を写し込み、両端をタップして
長さを入れると、その静止画の縦尺が決まり直ります。平面を法線方向に k 倍動かすので、
既に測った候補も以後の計測も同じ倍率になります。倍率は記録（CSV の「縦尺補正」列）に残ります。
**絶対幅を出す計測では必ず使ってください。** 目印の位置精度は ±2 px（0.2 mm / 100 mm ＝ 0.2%）で、
LiDAR の 3% より 1 桁良い。

同じ校正で、幅は設計値より **+0.1〜0.27 mm** 広く出ました（0.3〜5.0mm の 8 本、
0.095〜0.120 mm/px）。超過は幅に比例せずほぼ一定です。

縦尺そのものは疑わしくありません。同じ静止画で 60 mm の線の延長が 61 mm・59 mm と
出ており、**この静止画のスケールは ±2% で合っています**。つまり超過はスケールでは
なく幅の測り方（§4 の b）に乗っています。原因は「印刷の線が 0.15〜0.2 mm 太い」か
「端末が一定量だけ太く測る」のどちらかで、**幅の値だけでは分けられません**。
クラックスケール（実幅が保証された線）で幅校正を行うと決まります。

## 7b. 立ち位置のずれが作る「見かけの変位」（視差）

2時期比較では、幅ではなく**変位**を測ります。ここで効いてくるのが立ち位置です。

段階1のホモグラフィは**平面を厳密に合わせられる**ので、平らな壁ならどこから
撮っても重なります。合わないのは面から出っ張った所です。

    見かけの変位 ≒ 立ち位置のずれ × 凹凸の高さ ÷ 撮影距離

検出限界 0.105mm（σ=0.035mm の 3σ）を超えないための許容ずれ:

| 凹凸 | 3m | 5m | 10m | 25m |
|---|---|---|---|---|
| 5mm | 6.3cm | 10.5cm | 21.0cm | 52.5cm |
| 10mm | 3.1cm | 5.2cm | 10.5cm | 26.2cm |
| 20mm（大谷石の肌） | 1.6cm | 2.6cm | 5.2cm | 13.1cm |
| 40mm | 0.8cm | 1.3cm | 2.6cm | 6.6cm |

**再訪ガイドではこれを止められません。** ガイドは画像の一致しか見ておらず、
小角度では並進と回転がほぼ縮退するので、画像が合っていても横にずれていることが
あります。視差を作るのは実際の並進です。

### 点群による補正（`src/parallax.js`）

カメラが T だけ動いたとき、奥行き Z の点の画像上の動きは
`d(Z) = (1/Z)(−f·Tx + x·Tz, −f·Ty + y·Tz)`。平面ぶんは段階1が吸うので、残るのは

    残差 = g·(−f·Tx + x·Tz, −f·Ty + y·Tz),   g = 1/Z − 1/Z0

g は点群から決まる既知量なので、残差は T について**線形**。未知数3つに対して
セルは数十あるので最小二乗で解けます。**立ち位置を測る機材は要りません** —
視差そのものが、どれだけずれたかを語っています。

合成画像による検証（`web/test/parallax-e2e.mjs`、距離5m・7.14mm/px・
全面がざらついた面・凹凸 ±20mm）:

| 条件 | 補正なし | 補正あり | 推定したずれ（真値） |
|---|---|---|---|
| 同じ位置 | 偽陽性 0/53 | 0/53 | 0mm（0） |
| 横に 20cm | 偽陽性 12/47 | **0/47** | 170mm（200） |
| 石が 1.0mm 動いた | 本物 1/1 検出 | **1/1 のまま** | 0mm（0） |
| 横 20cm ＋ 石が 1.0mm 動いた | 偽陽性 14/47 | **0/47・本物は残る** | 172mm（200） |

### 視点をどこに置くか（近づいてスキャンし、離れて撮る）

点群と写真を橋渡しするには、**写真を撮った視点**が要ります。既定ではこれを
点群の原点（＝スキャン開始地点）としています。ところが LiDAR の実用距離は 3m
程度しかないので、高所・遠方の壁では近づいてスキャンし、離れて撮ることになる。

合成検証（距離 5m・7.14mm/px・横 20cm のずれ）で、スキャン開始位置だけを変えた結果:

| スキャン開始位置 | 点群が言う mm/px | 距離 | 補正後の偽陽性 | 推定ずれ |
|---|---|---|---|---|
| 写真と同じ位置 | 7.11（真値 7.14） | 4.98m | 0/47 | 170mm |
| **壁から 1m**・写真は 5m | **1.40** | **0.98m** | **11/47** | **1mm** |
| 距離は同じ・横に 1m ずれ | 7.41 | 5.08m | 0/47 | 173mm |

**壊れるのは奥行きの誤りだけです。**横に 1m ずれても（視線が 11° 傾く）補正は
効いています。奥行きの誤りは高さマップの倍率そのものを変えるので、石1個（300mm）
に対して 5倍ずれれば別の場所の凹凸を読むことになる。

そこで**撮影距離を手で入れられる**ようにしてあります（`placeViewpoint`）。視点を
「面から正対でその距離」に置き直すだけ。横方向に強いので歩測で足ります。
入れていないときは点群シートに警告を出します。

補正を当てても場が 10% 未満しか減らなければ `ineffective` を立て、比較シートで
「視差はほとんど減りませんでした」と言います。**引いたのに減らないのは補正では
なく無効化**で、黙って「補正しました」と出すのが一番悪い。

### 効かせてはいけない場合

凹凸が画面の一部にしか無いと、**そこに載っているセルの大半が本物に動いた
ブロック**だったときに、当てはめが本物を視差と誤って説明します。合成検証では
実際に 1.0mm の本物の変位を丸ごと消しました（推定ずれ 158mm を捏造）。

そこで面の質を測り、足りなければ**断ります**。

- `coverage` — 視差の効くセルが全体に占める割合。偏った盤面 0.17〜0.19 /
  全面がざらついた盤面 0.65〜0.83。しきい値 0.4
- `spread` — 効くセルの散らばり ÷ 全セルの散らばり。偏 0.35〜0.48 / 全面 0.99〜1.01。
  しきい値 0.6

ICP を安定域だけで解くのと同じ話で、**流用してよいのは動いていない側の特徴だけ**です。

### 残る誤差

補正は視差の 60〜65% を落とします（場の RMS 0.353→0.134mm）。引いた以上その
推定誤差は限界に乗るので、セルごとの標準誤差を `parallaxSePx` として返し、
3σ の判定に足しています。

## 8. 検証の方法

`swift test` で走る合成画像テストは、既知幅のひび割れに対して:

- ボケなしの理想画像で半値幅が真幅と ±0.3px 以内で一致すること
- 照明ムラを入れても幅が変わらないこと
- スケール適用後に mm 値が正しいこと（GSD 0.1mm/px × 4px = 0.4mm）
- 斜め壁面でスケールの異方性が理論値と一致すること
- 分解能不足のケースでフラグが立つこと

を確認しています。

実機での検証には次を推奨します。

1. 幅が既知の線を壁に貼り、複数の距離・角度で撮影する。
   - 0.5mm 以上: **[クラックゲージシート](https://kiyoshi-terrain.github.io/crack_tracking/gauge/)**
     （`web/gauge/`、A4 原寸印刷。0.3〜5.0mm の線とくさび）。印刷の線は
     0.03〜0.05mm 太るので、印刷後にルーペ付きクラックスケールで実幅を読んでおく
   - 0.1〜0.3mm: 市販の標準クラックゲージ（透明板）。印刷では出せない
2. 計測値と真値の差を距離・角度別に整理する。
3. アプリの「幅校正」で、太い線と細い線の 2 本の実幅を入れる（§4）。
   σ と一定の太り b が分かれて決まり、案件に残る。コードの既定値は触らない。
   超過が幅に比例して増えるなら、それはスケール（LiDAR 距離）の問題なので
   先に「縦尺」を合わせる。
